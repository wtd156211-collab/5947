# 设备事件会话化

输入是设备上报的事件流，按用户切分会话：同一个用户超过半小时没有新事件就断开，下一条算新会话，最后给出每个会话的开始时间、结束时间、时长和事件数。

线上一天的文件两百多万行，必须边读边处理，内存不能跟着行数涨（留了六十四兆余量），所以别想着先全部读进来排个序。上游上报有延迟，文件里的事件不保证严格按时间顺序，同一毫秒内的先后也可能是乱的，现阶段允许几分钟以内的乱序，这条要当成常态处理，不能假设输入已经有序。输出必须稳：同一份输入跑两遍逐字节一致，换台机器也一样。库里还要放一个笨办法——全部读进来排好序再切会话——只给测试用，不参与正常路径，也不许被正常入口调用；测试里随机造带乱序的数据让两边对拍。测试里要有能放大到几十万行的用例，内存那条要真的去测峰值，不是写句注释就算。实现只用标准库，测试用 unittest。

## 输入格式

CSV，每行一条事件，三列：

```text
timestamp,user_id,event_type
2026-09-22T10:00:00.000Z,u1001,connected
```

`timestamp` 是 UTC 的 ISO-8601，毫秒精度；`user_id` 与 `event_type` 都不含逗号。

乱序约定：一条事件的时间戳，不比它在文件里之前出现过的最大时间戳早超过 5 分钟（允许 5 分钟以内的迟到）。

## 切分规则

- 按 `user_id` 分别处理，用户之间互不影响。
- 同一用户的相邻事件，间隔**严格大于** 30 分钟（1800000 毫秒）才断开，下一条开一个新会话；正好 30 分钟仍属于同一个会话。
- 会话的开始、结束时间取该会话内最早、最晚事件的时间戳。
- `duration_ms` = 结束时间 − 开始时间，单位毫秒。
- `event_count` = 会话内的事件条数。

## 同时刻的先后

- 同一用户、同一毫秒的多条事件，按它们在输入文件里的行序处理。这条规则是显式写死的，既不依赖字典序，也不依赖遍历顺序；它只影响内部处理顺序，不影响会话边界和统计结果。
- 不同用户在同一毫秒的事件互不影响。
- 输出顺序：按会话结束时间升序；结束时间相同的，按 `user_id` 升序（按 UTF-8 字节序比较，这两条是文档里写明的固定规则，不是巧合）。

## 输出格式

CSV，一行一个会话，表头固定：

```text
user_id,session_start,session_end,duration_ms,event_count
u1002,2026-09-22T10:01:00.000Z,2026-09-22T10:31:00.000Z,1800000,2
```

时间戳格式与输入一致（UTC、毫秒精度），行尾 LF。

## 样例

- `samples/case-1.events.csv` / `samples/case-1.sessions.csv`：顺序输入，含同一毫秒的并列事件，以及间隔正好 30 分钟的边界。
- `samples/case-2.events.csv` / `samples/case-2.sessions.csv`：含 5 分钟以内的乱序（其中一条正好迟到 5 分钟）、同一毫秒的并列事件、正好 30 分钟与超过 30 分钟两种边界。

期望输出是照上面规则算出来的，格式照着这两个文件来。
